Forms

Validate a form and redraw it when it fails

Propagate the error and the framework does the rest — a browser is redirected back to the form with the messages and the old input, and a JSON client gets a 422 in Laravel’s shape. One handler serves both.

pub async fn store(mut req: Request) -> Result<Response, Errors> {
    let data = validate(&mut req, &[
        ("title", "required|max:120"),
        ("body",  "required|min:10"),
    ]).await?;

    let db = req.state::<Database>().expect("registered in main.rs");
    let mut post = Post {
        title: data.string("title").unwrap_or_default(),
        body:  data.string("body").unwrap_or_default(),
        ..Default::default()
    };
    post.insert(db).await?;

    Ok(Response::see_other(format!("/posts/{}", post.id)))
}

The form reads what the failed request left behind:

pub async fn create(req: Request) -> Result<Response> {
    req.view("posts/create", &ViewContext::new()
        .with("errors", req.errors())
        .with("old", req.old()))
}
<form method="post" action="/posts">
  {!! csrf_field !!}
  @if(errors.title)<p class="error">{{ errors.title.0 }}</p>@endif
  <input name="title" value="{{ old.title }}">
  <button>Publish</button>
</form>

The old input never contains a password, or anything else whose field name looks like a secret. Re-filling a password box means putting the password back into HTML, and that HTML ends up in caches, in browser history and in screenshots.

Validate something that is not a form field

validate reads the request body. When the values are already in hand — normalised, or assembled from several places — build the validator directly:

    .errors();

Files

Accept an upload and serve it back

Needs storage.

pub async fn avatar(mut req: Request) -> Result<Response> {
    let storage = req.state::<Storage>().expect("registered in main.rs");

    let Some(file) = req.file("avatar") else {
        return Ok(Response::new(Status::BAD_REQUEST).with_text("No file was sent."));
    };
    // Never trust the filename the browser sent: it can contain a path.
    let name = format!("avatars/{}.png", rustlavel::auth::random::hex(16));
    storage.put(&name, file.bytes()).await?;

    Ok(Response::see_other("/profile"))
}

Uploads belong under storage/app, outside the web root. To make a subset of them reachable over HTTP, write them under storage/app/public and link it once:

rustlavel storage:link

Set a per-route upload limit

The server has a body limit that protects the process, and it has to be as large as the biggest upload the application accepts anywhere. BodyLimit is the policy on top:

r.group("/api", |api| {
    api.middleware(BodyLimit::kilobytes(64));   // JSON endpoints
    …
});
r.post("/avatar", upload).middleware(BodyLimit::megabytes(5));

Data

Paginate a listing

Needs db.

let page = req.query("page").and_then(|p| p.parse().ok()).unwrap_or(1);
let listed = Post::query().latest("id").paginate(db, page, 20).await?;

req.view("posts/index", &ViewContext::new()
    .with("posts", listed.to_json()))

Past a few hundred thousand rows the count query starts to hurt. Cursor pagination has no count and stays correct while rows are being inserted underneath the reader:

let page = Post::query()
    .cursor_paginate(db, req.query("cursor"), 20)
    .await?;

Return JSON with one shape per type

pub struct PostResource;

impl JsonResource for PostResource {
    type Model = Post;

    fn to_json(post: &Post) -> Json {
        attributes()
            .set("id", post.id)
            .set("title", post.title.as_str())
            .when(post.published, "published_at", || Json::from(post.published_at.clone()))
            .finish()
    }
}

// In a controller:
PostResource::collection(&listed.hydrate::<Post>()?)
    .paginate(listed.current_page, listed.per_page, listed.total)
    .path("/api/posts")

A when() that is false leaves the key absent, not null. A client told "published_at": null has to work out what null means; a client not told about it knows it is not published.

Run several statements as one

let mut tx = db.begin().await?;
tx.execute("update accounts set balance = balance - ? where id = ?", &[amount.into(), from.into()]).await?;
tx.execute("update accounts set balance = balance + ? where id = ?", &[amount.into(), to.into()]).await?;
tx.commit().await?;

Dropping the transaction without committing rolls it back, so an early ? leaves nothing half-applied.

Talking to other services

Call an API without making an outage worse

Needs client.

let http = Client::new().retries(2).breaker(CircuitBreaker::new());

match http.get("https://api.example.com/rates").send().await {
    Ok(response) => use_them(response.json()?),
    // Nothing was sent, so nothing can have had an effect — which is
    // exactly when falling back to a cached answer is safe.
    Err(Error::Unavailable(_)) => cached_rates(),
    Err(error) => return Err(error),
}

mailer.send(

assert_eq!(fake.count(), 1);

Sign somebody in through Google or GitHub

Needs oauth.

r.get("/auth/github", |req: Request| async move {
    let provider = req.state::<OAuthClient>().expect("registered in main.rs");
    let (url, verifier) = provider.authorize_url(&["read:user"]);
    // PKCE: the verifier stays here, only its hash goes to the provider.
    req.session().put("_pkce", Json::from(verifier));
    Response::see_other(url)
});

Operating it

Turn something on for some people

Needs flags.

if req.flag("new-checkout").await? {
    return new_checkout(req).await;
}

And when it goes wrong at three in the morning, without a deploy:

FLAGS_OFF=new-checkout

Take a new release of the starter kit

rustlavel upgrade --dry-run
rustlavel upgrade

Three-way, not two: the version you started from, what you have now, and what the release ships. Changes only one side made apply on their own; changes both sides made are written with conflict markers so the build fails rather than an upgrade half-applying. Files the kit never wrote are never touched. See the guide for the flags.

Answer a load balancer

App::new()?.plugin(
    Health::new().check("database", |req| {
        let db = req.state::<Database>().cloned();
        async move {
            db.ok_or("no database")?
              .scalar::<i64>("select 1", &[]).await
              .map(|_| ()).map_err(|e| e.to_string())
        }
    }),
)

GET /up says the process is alive and is what restarts it. GET /up/ready runs the checks and says whether it can do useful work, and is what routes traffic to it. Pointing a liveness probe at the second one turns a database outage into a restart loop.

Find out why a request was slow

App::new()?
    .middleware(RequestId::new())     // one id, in the log and on the response
    .plugin(Telescope::default())     // /telescope, refuses to mount in production
    .plugin(Debugbar::default())      // this page's queries, drawn on the page

The identifier on the response is the one to ask a user for: it appears in every log line for that request and on the http.request event that Telescope, the metrics endpoint and the OTLP exporter all read.

Testing

Exercise a route without a socket

#[rustlavel::test]
async fn a_guest_cannot_reach_the_dashboard() {
    let client = app().test_client();
    let response = client.get("/dashboard").await;
    response.assert_redirect("/login");
}

#[rustlavel::test]
async fn a_bad_form_comes_back_with_its_errors() {
    let client = app().test_client();
    client.get("/posts/create").await;
    client.post("/posts", &[("title", "")]).await.assert_status(303);
    client.get("/posts/create").await.assert_see("The title field is required.");
}

Test against a real database, or skip cleanly

The pattern the framework uses on itself: a suite that needs a server reads its URL from the environment and reports a skip when there is none, so cargo test stays green on a laptop with no Docker.

macro_rules! server {
    ($variable:literal) => {
        match std::env::var($variable) {
            Ok(url) if !url.is_empty() => url,
            _ => { eprintln!("skipping: {} is not set", $variable); return; }
        }
    };
}

Give every test its own name-spaced rows or tables. The suite runs concurrently, and two tests sharing a fixture fail in a way that looks like a bug in the code rather than in the tests.
